Detailed Description

TMC9660 telemetry snapshots, fault decoding and parameter-image apply for MotorController.

The hooks the drive-observability design (hardfoc-vortex-v1 docs/design/drive-observability.md) needs from the HAL, independent of any protocol stack:

  • Batch access. Every read and write goes through the driver's pipelined TMCL batch API (readParameters() / writeParameters()): on SPI, N accesses cost N + 1 datagrams instead of 2N (design §1.8).
  • Telemetry snapshots (§1.3, §2.2, §2.3): a caller-owned MotorTelemetrySnapshot is refreshed in place from one batch. Every field remembers the sequence number of its last good read, so a consumer can tell its age; a failed access leaves the old value and does not move its stamp. The cyclic set is the design's fixed slots: position and velocity actual, packed Iq/Id (331), status (289), and the general / gate-driver error words alternating (299 / 300).
  • Fault decoding (§1.5): the four status words become named conditions and a severity.
  • Configuration (§4.3–§4.5): a parameter image is applied with MOTOR_TYPE first (the chip rejects most SAPs until it is set), optionally only where the chip differs (differential apply), and optionally read back and compared (verify).

Everything here is templated on the driver type (Tmc9660Handler::SpiDriver or UartDriver) and is called by MotorController inside Tmc9660Handler::visitDriver(), so the handler mutex is held. Units are the chip's raw units; the SI conversions given are those the design marks as solid. The packed 331/332 values are unscaled until calibrated (§1.4).

Ownership: value types and free functions. Thread safety: none of its own (callers hold the handler lock). No allocation: batches are chunked through a fixed stack buffer. MCU-free.
