# Initialisation

`Vortex::EnsureInitialized()` brings every manager up, one at a time, in a fixed order. Call it once, early in
`app_main()`, before you touch any manager.

The order follows the dependencies: storage first, so configuration and calibration can be read early; then the
buses; then the GPIO pins, which include the PCAL95555 expander lines the TMC9660 needs; then the status LED, early
so an LED-only bench works without the motor controller. After that come the managers that depend on the TMC9660:
`AdcManager` reads its channels through the TMC9660, and `TemperatureManager` reads the NTC through `AdcManager` and
the chip temperature from the TMC9660.

## What happens when a step fails

- **Required steps (NVS, comms, GPIO, LEDs).** If one fails, `EnsureInitialized()` logs an error, stops and returns
  `false`. `IsInitialized()` stays `false`, and calling `EnsureInitialized()` again retries from the start.
- **Best-effort steps (motors, ADC, IMU, encoders, temperature).** A failure is logged as a warning and the manager
  stays unavailable; the remaining steps still run and `EnsureInitialized()` returns `true`. The log then says
  `Initialized in degraded mode` and lists which of Motors, ADC, IMU, Enc and Temp are `OFF`. Check
  `vortex.motors.IsInitialized()` (or the [diagnostics](errors.md)) before relying on a best-effort manager.

This lets a bench with only some chips fitted, or with the motor supply off, still come up and log.

## The onboard TMC9660 and its transport

Step 5 creates the onboard TMC9660 before initialising `MotorController`. It takes the four TMC9660 control lines
(reset, driver enable, fault, wake) from `GpioManager`, which is why GPIO comes first, and registers the chip on one
of two host links:

| Transport | How to select it | What happens |
| --- | --- | --- |
| UART (default) | nothing | TMCL over the UART at TMCL address 1; the SPI mux pin `PCAL_TMC_SPI_COMM_EN` stays released |
| SPI | `Vortex::SetOnboardTmc9660Transport(VortexOnboardTmc9660Transport::Spi)` **before** `EnsureInitialized()` | TMCL over SPI2; `MotorController` asserts the SPI mux while it talks to the chip |

`SetOnboardTmc9660Transport()` is ignored (with a warning) once initialisation has completed.

## Calling a manager directly

Every manager has its own `EnsureInitialized()`, which returns `true` at once if the manager is already up. Code that
uses one manager on its own can call it, but going through `Vortex::EnsureInitialized()` gives the right order, the
onboard TMC9660 registration and the system diagnostics. `EncoderManager` creates no device by itself; see
[EncoderManager](../managers/encoders.md).

## Shutting down

`Vortex::Shutdown()` de-initialises every initialised manager, in this order: temperature, LEDs, encoders, IMU, ADC,
motors, GPIO, comms, NVS. That is the start-up order reversed except for the LED manager, which is shut down second
although it starts fourth. It then clears the initialised flag, so a later `EnsureInitialized()` starts again from
the beginning. It returns `false` if the HAL was not initialised.
